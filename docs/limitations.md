# Limitations

Everything this project has **not** established, in one place.

The per-phase docs each carry a "what this does not establish" section. A
reviewer should not have to assemble them from four files, and a limitation
that is hard to find reads as a limitation someone hoped would not be found.

Read this alongside the results, not after them.

---

## The one that qualifies everything else

**Every number in this project comes from synthetic data.**

| Corpus | Source | Real? |
|---|---|---|
| `gst_in_synthetic` | Generated by `scripts/generate_synthetic_gst_invoices.py`, rendered by our own renderer | No |
| `fatura2` | Third party (Limam et al., CC-BY-4.0), 50 layout templates | Third-party, but still **template-generated** |

FATURA2 matters because it was designed by other people — it is what exposed
the extraction baseline scoring 1.000 on our invoices and 0.559 on theirs. But
it is not photographs. Nothing in this project has met a real scan: no stamps,
handwriting, staples, folds, coffee rings, phone-camera perspective, non-Latin
script, or the specific ways real print degrades.

**SROIE** (real photographed receipts) and **CORD** remain unconverted. They
are the single highest-value acquisition left.

## The VLM has never been run

`src/invoice_extract/models/vlm.py` is written against the transformers API and
unit-tested through an injected fake model and processor. That covers prompt
construction, response parsing and coercion. It does **not** establish that the
generation call is correct.

There is no GPU on the development machine. One Colab run was executed and its
output discarded, because it used a prompt template containing a placeholder
value (`123.45`) that Qwen2-VL-2B copied verbatim in 8 of 8 responses. The
prompt is fixed; the run has not been repeated.

**Any VLM number quoted anywhere in this project is therefore either absent or
stale.** The demo renders "not run" rather than showing the superseded figures.

## Phase 1 — preprocessing and OCR

- **Both exit criteria failed.** CER never reached < 8% on noisy pages (best
  `medium` is 0.0812 against a 0.0800 target; `heavy` is 0.4284), and
  preprocessing improves CER on `heavy` only, by 1.1 points. Reported as a
  result, not deferred.
- **The criteria were written against the wrong metric.** The full chain minus
  binarisation raises *word accuracy* 14.1 points on heavy pages while nudging
  CER the wrong way. Word accuracy is what Phase 2 depends on, because
  extraction needs to know *which field* a value belongs to, and that is
  spatial.
- **The first sweep, at n = 4, ranked the pipelines wrongly.** Re-running at
  n = 15 changed which pipeline wins in 4 of 6 metric/profile cells, and the
  headline deskew effect on `heavy` shrank from +21.6 to +11.0 points. Every
  qualitative conclusion survived; no magnitude did. Per-cell variance at n = 4
  exceeded the differences the ranking was built on, which is a caution about
  every thin cell in this project, not just that one.
- **Preprocessing is a net loss on clean pages** (word accuracy 0.5733 raw
  versus 0.4842 for the full chain) and the pipeline applies it
  unconditionally. Nothing decides whether a page is degraded enough to need
  it.
- **Detection metrics penalise tokenisation, not just recognition.** PaddleOCR
  splits punctuation into separate tokens (`Salai` `,`), so predicted word
  counts run ~1.8x gold and precision drops for reasons unrelated to reading
  quality.
- **Only the PP-OCRv5 mobile models are measured** (`fast=True`, chosen for a
  2.6x speedup). Whether the larger PP-OCRv6 models rank the pipelines
  differently is open.
- **Tesseract is implemented but never benchmarked.** It needs a system binary
  that is not installed here.

## Phase 2 — extraction

- **No end-to-end accuracy number exists.** Every extraction result uses
  `--ocr-source gold`, which feeds the renderer's own text. That is a
  perfect-OCR **ceiling**, not an end-to-end measurement. Real figures will be
  lower.
- **FATURA2 has no line-item annotations.** Tag 10 is a single `table`
  placeholder covering the whole region, so every converted document carries
  `line_items: []`. The line-item exit criterion is verified **only on our own
  corpus**, where it is least meaningful.
- **The FATURA2 tag vocabulary was inferred, not supplied.** The parquet ships
  bare integer `ner_tags` with no label names. The mapping was derived by
  auditing all 1,400 test documents; `--audit-tags` re-verifies it and fails if
  a release renumbers them. It remains an inference.
- **The rules baseline is tuned to a renderer we wrote.** Its rules are
  label-anchored rather than position-anchored to limit this, and FATURA2
  quantifies how much it still flattered: 1.000 at home, 0.559 away.
- **Single-page only.** The page-retrieval step from refs [3] and [4] is
  untouched.

## Phase 3 — RAG enrichment

- **The detectors catch what they were designed to catch, and nothing else.**
  Two scenarios were held out deliberately, and **both were missed completely**:

  | Held-out scenario | Caught |
  |---|---|
  | `line_item_padding` (line total inflated, invoice still reconciles) | **0 / 4** |
  | `gstin_state_contradicts_address` (state code vs. billing state) | **0 / 3** |

  Recall is 1.000 on designed-for scenarios and **0.800** once these are
  included. They are kept unfixed as a permanent probe: closing them and
  re-reporting 100% would reproduce the circularity they exist to expose.
- **Tiny label space.** Three accounts, ten item descriptions. Real charts of
  accounts run to hundreds of codes, and the hard cases are near-neighbours
  ("software subscription" vs "IT equipment") that this corpus does not contain.
- **No LLM is involved.** The plan describes an LLM assigning a category from
  retrieved context. This retrieves and takes a similarity-weighted vote.
- **Dense retrieval is untested.** TF-IDF character n-grams are what has been
  measured; the `Retriever` interface is ready for embeddings but nothing has
  been run through it.
- **273 ledger entries.** Exact nearest-neighbour search is fine at this size
  and will need an approximate index at production scale.

## Phase 4 — vendor validation

- **Four fraud scenarios, all injected by us.** Same caveat as Phase 3, without
  the held-out probe — adding one here is open work.
- **63 synthetic suppliers.** No name collisions, no mergers, no subsidiaries
  sharing a GSTIN, no legitimate bank-detail changes with paperwork behind them.
  All of those are routine in a real supplier file and all would produce
  findings this system would call fraud.
- **No vendor aliasing.** A real master carries known trading names; this
  matches on string similarity alone.
- **`address_mismatch` is never exercised.** The generator gives each supplier
  exactly one address, so the check never fires and its 75% threshold is
  unvalidated.
- **Duplicate detection is O(n) over history per invoice.** Fine at 100
  documents, needs an index in production.
- **An impostor vendor is indistinguishable from a legitimate new supplier.**
  On the invoice alone there is nothing to tell them apart — no record, no
  history, nothing to compare. The system raises `unknown_vendor` for both,
  correctly. Separating them requires an onboarding process outside this
  pipeline. `impostor_vendor` is therefore excluded from the scored fraud set;
  counting it would score 100% by construction.
- **Performance degrades with thin history, in a specific way.** At a
  50-invoice history: precision **0.778**, false-positive rate **0.214**. More
  vendors sit just above the two-invoice threshold where identity checks switch
  on but the record is still thin — enough history to be checked, not enough to
  be right.

## Phase 5 — service and human review

- **No authentication or authorisation — out of scope by decision.** The
  service accepts a reviewer name as a plain string. An override of a FAIL is
  *recorded* against a name, not *verified* against an identity, so anyone who
  can reach the port can make a blocked invoice payable under any name. It binds
  to 127.0.0.1 by default. Putting it in front of real users needs an identity
  provider, role separation (whoever uploads must not be able to override), and
  audit retention; none of that is built.
- **The synchronous endpoint is not under 10 s with real OCR.** OCR is ~40 s a
  page on CPU. The exit criterion is met only by the job endpoint returning a
  handle immediately.
- **One correction does not teach the categoriser.** Measured: it took 3
  reviewed corrections of the same novel item before a later invoice was
  categorised without help, because Phase 3's vote lets several weak same-vendor
  neighbours outvote one near-exact match. The fix belongs in Phase 3.
- **With real OCR every page went to review** (6/6 on the timing run): OCR
  misreads of unit prices surface as price deviations and arithmetic flags. The
  auto-accept path is mostly exercised only with perfect text.
- **Accretion trusts auto-accepted documents.** A fraud that passes Phase 4 is
  added to the vendor master as normal history.
- **No load testing, one OCR worker, in-memory job registry** (jobs are lost on
  restart; the documents and decisions are not).
- **Single-page documents only.**
- **No reviewer study.** Whether the queue gives a person enough to decide well
  is untested.

## Statistical weight

| Experiment | n |
|---|---|
| Phase 1 ablation | 15 documents per cell |
| Phase 2 synthetic | 150 documents |
| Phase 2 FATURA2 | 300 documents |
| Phase 3 | 100 ledger / 50 evaluation |
| Phase 4 | 100 history / 50 evaluation |

Phase 1 is the thin one, and it is the one case where the thinness has been
measured rather than assumed: the first sweep ran at n = 4 and got the pipeline
ranking wrong in 4 of 6 cells. At n = 15 the 14-point word-accuracy effect on
`heavy` is well clear of the noise; differences under about 2 points between
adjacent pipeline rows are not, and should be read as ties rather than as an
ordering.

## The corpus has been wrong three times

Each was found only because a later phase depended on the data being right, and
each would have invalidated the phase that found it:

| Defect | Found in | Effect if unfixed |
|---|---|---|
| GSTIN check digits drawn at random (295/300 invalid) | Phase 2 | Checksum validation useless — fires on everything |
| `line_total` tax-inclusive; both checks double-subtracted discount | Phase 2 | 46/150 documents flagged; line-item arithmetic unusable as a signal |
| Vendor identity re-rolled per invoice (0/45 stable GSTIN or bank account); prices 57% spread; invoice numbers colliding | Phase 4 | Vendor master impossible; bank-change detection fires on every invoice |

This is itself a limitation: **a generator can only be validated by something
that consumes it.** Phases 5 and 6 may yet surface a fourth.

## What would move the needle most

In order:

1. **Run the VLM.** One Colab session. It is the single largest unmeasured
   claim in the project.
2. **Convert SROIE.** Real photographed receipts would be the first time any
   stage here meets a real scan.
3. **Measure end-to-end**, not against the perfect-OCR ceiling.
4. **Add a held-out fraud scenario to Phase 4**, matching the Phase 3 probe.
